Intra-function code generation

What You Need To Do

For this project you are required to fill in the functions assignment and ifStatement in the Grammar.cpp file.  Both functions have a TODO comment so you can easily find them.  You will need to read through the code to learn how it works, and develop an understanding of how code generation works.  You do not need to create any additional methods or modify any other part of the program for it to work.  You are graded on your implementations of the 2 functions.  If they are implemented correctly the program will work as described in the description section.  You must follow the submission requirements listed in What to submit. 

Description

This part is the description on what the completed code generator shall look like. Some of the requirements may be already implemented in the incomplete code generator that you get. Modify the parser to generate assembly-like code for each function in an input program.  In another word, you are supposed to write a code generator, which, takes an original program as input, parses it, and then generates the code that can be represented by the modified grammar. Note, the modified grammar is not going to be used by your parser. It is for you (as a programmer) to understand what the output program should look like. The specific requirements are as follows.
  • As in previous projects, your parser should ignore (but copy) "meta-statements" to the output program.
  • The output program uses the same grammar as the input program with the following modifications.  (The input program will be the same set of programs used in the previous two projects, following the original grammar.)
  • Grammar modification for data declaration:
    • No data declaration is allowed except one array at program level and one array inside each function. You may assume only "int" type is used including the type of the function returning values.
  • Grammar modification for assignment and expression:
    • <assignment> --> <id> equal_sign <operand> <operation> <operand> semicolon | <id>equal_sign <operand> semicolon | <id>equal_sign<func call>
    • <operand> --> NUMBER | minus_sign NUMBER | <id>
    • <operation> --> <addop> | <mulop> | <comparison op> | <condition op>
    • Change all mentioning of <expression> with <operand>, as in <id>, read/write statement, <func call>, <return>, and <condition>.
    • Now <id>s are array references.
  • Grammar modification for control flow:
    • <if-statement> --> if left_parenthesis <operand> <comparison op or condition op> <operand> right_parenthesis goto LABEL semicolon
    • <goto-statement> --> goto LABEL semicolon
    • <label-statement> --> LABEL colon semicolon
    • LABEL is just another name for ID token
    • Do not use the previous definition of <if-statement>.  Do not use <while-statement>, <break>, and <continue>. You will have to use the allowed constructs (e.g., if, goto, label) to implement what these disallowed constructs try to implement in the original program.
  • Grammar modification for functions:
    • Function declaration and definition remain unchanged.
    • In <func call>, each parameter must be <operand> instead of <experssion>.
    • In <return>, use <operand> instead of <expression>.
  • The output program should be compilable by the gcc compiler in our VCL image, and have the same behavior as the input program has. An exception is precision loss due to the usage of int types (e.g., original has b=1/3*3; your generated code is loc[0]=1/3; loc[1]=loc[0]*3. Your code could give 0 for loc[1] rather than 1 in the original). Such loss is acceptable.
  • The name of the generated program should have "_intraGen.c" or "_gen.c" as the suffix (e.g., "foo.c" becomes "foo_intraGen.c" or "foo_gen.c).
  • You may make the following assumptions about the input programs: (1) Array declarations can have only constant as the size. For instance, "int A[30];" can appear in the input program, but "int A[x];" or "int A[x+y]" or "int A[3+4]" will not. (2) Array elements can be passed as parameters of a function call, but arrays cannot. For instance, A is an array (which can be only one dimensional). A function call like "foo(A);" will not appear in the input program, but "foo(A[x+y]);" could. (3) Your can assume that the input program is valid if it passes through the scanner and parser.

What to submit

  • You must submit your solution in a .tar file.  NOT zip, tar.gz, tgz or rar it needs to be .tar.  The file name needs to be unityID.tar, where unityID is your unity ID. 
  • You can NOT have any compressed folders inside the tar.  This is to facilitate automation. 
  • You must submit the code in the same folder structure it was provided to you in.  Do NOT create your own subdirectories.  If you change the names or layout of the folders or files, your solution will not be evaluated.  This is done to make the submissions consistent to allow for automation. 
  • Do Not include your write-ups inside code sub-folders, they should be in the top level. 
  • We are providing you with a Makefile to compile your solution. When you submit your solution the Makefile must be there. 
Submit the complete solution in a .tar file.  Include a ReadMe describing your implementation and the changes you made.  The README should just be of what you did.  Do Not include the any files that are the result of compilation or testing.  All other submission instruction is the same as in the Scanner project.

  • Your code only needs to support all the language features used in the sample programs. The test programs we use will not include new langauge features. So if you are thinking of some complicated scenario to handle, you may wnat to first check the sample codes to see whether that scenario exists in them.
  • In your scanner project, you were asked to put csc512 prefix to IDs. In this project, no such prefix is supposed to be added.
  • Again, your output program does not have to be exactly the same as the example output we gave, as long as your output meets the form we required in the project description. For instance, rather than "return local[0]", you output "return 1" in the 3rd example, it is okey.
  • The size of the global and local arrays can be larger than what the program needs.
